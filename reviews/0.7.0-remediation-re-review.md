## Blockers

### B1 — `threshold` default is broken: an absent attribute now yields 0, not 50 *(verified; reproduced again in triage)*

`src/tosi-product.ts:740`

```js
const parsed = Number(this.getAttribute("threshold"));
const threshold = Number.isFinite(parsed) ? parsed : 50;
```

`initAttributes` declares `threshold: 50` as a **property**; it does not reflect the default to the DOM. So `getAttribute("threshold")` returns `null` for every header written without the attribute, `Number(null)` is `0`, `Number.isFinite(0)` is `true`, and the guard accepts it. Every `<tosi-product-header>` with no `threshold` now becomes visible at `scrollY > 0`. The only way to reach 50 is to write an *unparseable* value (`threshold="banana"`) — the default and the error case are inverted.

Regression from this release: `git diff v0.6.5...HEAD` shows the prior line was `Number(this.getAttribute("threshold")) || 50`, where `|| 50` was the only thing supplying the default. It falsifies two shipped statements — `src/tosi-product.ts:43` ("default `50`") and the CHANGELOG bullet "Both now fall back only on a missing or unparseable value".

**Drift, in the same commit:** `src/tosi-b3d-scroll.ts:52-55` adds `function num(attr, fallback)` that correctly guards `attr !== null && attr !== ""` first. The same diff wrote the helper right in one file and open-coded a broken variant in the other (which also mishandles `threshold=""`).

**Fix:** read the property, as the sibling `debug` fix in this same diff does — `const threshold = this.threshold;` — or share the `num()` helper. Add a regression test asserting absent → 50 and `threshold="0"` → 0. Re-review scope: correctness over the remediation diff only.

### B2 — Two breaking changes are missing from the Breaking section *(verified in this triage)*

The release has an explicit `### Breaking` heading and neither of these is in it.

**(a) `rgb()` / `hsl()` waypoint values silently changed output format.** Unifying `<tosi-interpolator>` on the theme kernel hoisted the color test above the numeric branch. Confirmed by running the shipped function:

```
interpolateStrings("rgb(0,0,0)", "rgb(255,255,255)", 0.5)
  → "color-mix(in srgb, rgb(0,0,0) 50%, rgb(255,255,255))"
interpolateStrings("hsl(0,0%,0%)", "hsl(200,50%,50%)", 0.5)
  → "color-mix(in srgb, hsl(0,0%,0%) 50%, hsl(200,50%,50%))"
```

These previously took the numeric path and emitted per-channel `rgb(127.5, …)`, valid everywhere. `color-mix()` is Baseline mid-2023 (Chrome 111 / Safari 16.2 / Firefox 113); the repo states no browser-support floor anywhere. On an older WebView the declaration is dropped and the element flashes to its unstyled value — the exact failure mode this release claims to have *fixed* for hex. Only hex got regression tests; the rgb/hsl path has none.

**(b) Public declarations moved out of the shipped `.d.ts` files.** Verified against both tags: `v0.6.5`'s `dist/tosi-product.d.ts` declared `isColor` (line 9) and `interpolateThemeValue` (line 17); HEAD's does not — they now live only in `dist/waypoints.d.ts`. 0.6.5 shipped exactly two declaration files, so `dist/tosi-product.d.ts` was a plausible deep-import target. The barrel still re-exports everything, so `import … from 'tosijs-product'` is unaffected, but a type-only deep import breaks with no migration note.

**Fix:** both are CHANGELOG edits, not code changes. Add (a) with the browser floor stated explicitly and a note that rgb/hsl now behave like hex; add (b) with the one-line migration (`import from 'tosijs-product'`, or `tosijs-product/dist/waypoints`). Add rgb/hsl regression tests alongside the existing hex ones while you are in there.

- [ ] **`tosi-mosaic --format jpg|png` feeds a 0–100 WebP quality into mjpeg's 1–31 qscale** *(major, verified)* — `bin/tosi-mosaic.ts:165`. Measured on a real clip: `-q 75` (default), `-q 90` and `-q 31` produce **byte-identical** output (same md5) because mjpeg clamps to the worst setting; only 2–31 moves the needle. For png, `-q:v` is inert entirely (`-q 1`/`75`/`100` all identical). The brand-new escape hatch for webp-less ffmpeg builds therefore emits worst-possible JPEGs by default, and the obvious remedy (`--quality 90`) is a no-op. Usage text at line 37 still says "WebP quality (default: 75)". Fix: map quality per encoder — jpg `qscale = clamp(round(31 - q/100*29), 2, 31)`, png `-compression_level` or nothing, keep `-q:v q` for webp only; update the help line; smoke-test that `-q 90` > `-q 30` in bytes.
- [ ] **`tosi-mosaic` truncates the mosaic to the front of the clip** *(minor, verified; also a completeness gap)* — `bin/tosi-mosaic.ts:139`. Grid is sized from `targetFrames` but `select` emits more. 90-frame source at `-f 60`: stride 1, total 60, grid 8×8 = 64 tiles, `tile` fills from inputs 0–63 and `-frames:v 1` drops the rest. Fix: derive the grid from `ceil(sourceFrames / stride)`, not from the request. Add a CLI smoke case for `targetFrames < sourceFrames < 2 * targetFrames`.
